⚙️ Protocolos de Acción Activos

La lógica de decisión en tiempo real de cada agente. Estos protocolos se ejecutan secuencialmente cada ciclo (cada 10 minutos). Nota: Los datos de abajo son teóricos/hardcodeados. Para traer datos en vivo, necesitamos conectar con /api/agent-status endpoint.

📋 CÓMO FUNCIONAN LOS PROTOCOLOS

P0 (Prioridad 0 - EMERGENCIA):
Si se cumple el trigger → Acción inmediata, no chequea P1 ni P2
Ejemplo: Si hambre > 85 → Ir a comer (ignora todo lo demás)
P1 (Prioridad 1 - MANTENIMIENTO):
Si P0 no se cumple Y P1 se cumple → Ejecuta P1
Ejemplo: Si ore >= 50 → Vender (para no saturarse)
P2 (Prioridad 2 - PRODUCCIÓN):
Si P0 y P1 no se cumplen → Ejecuta el trabajo normal
Ejemplo: Si en Hacker House → Hacer hacking

🔗 PRÓXIMO PASO: Conectar con API

Para que estos protocolos reflejen la realidad en vivo:

1. Fetch /api/agent-status cada 30s
2. Extraer valores reales: hunger, inventory, location, speed
3. Evaluar qué protocol se ejecutaría HOY con esos datos
4. Mostrar en verde si se cumple, gris si no
5. Agregar timestamp "Última actualización: hace X segundos"
🛠️ Árbol de Tecnología (Roadmap de Equipo)

Progresión de herramientas que cada agente puede comprar con cristales para mejorar su eficiencia. Datos actuales: Teóricos/hardcodeados. Necesitan conectarse con /api/skill/merchants.

🔍 QUÉ ES EL ÁRBOL DE TECNOLOGÍA

Es un roadmap de progresión que muestra:

COSTO: Cuántos cristales se necesitan
TIER: Nivel de herramienta (2, 3, etc)
EFECTO: Qué mejora (velocidad, capacidad, etc)

Ejemplo: Si BB-8 compra "Obsidian Pickaxe" (20 cristales):
→ Extrae cristales directamente en lugar de ore
→ Sube su XP/h de ~162 a ~200+

✓ Adquirido: El agente ya tiene esta herramienta (más opaco)

💰 CÓMO USARLO PARA ITERAR

1. Ver Próximo Objetivo:
    "BB-8 necesita 20 crystals para Obsidian Pickaxe"

2. Calcular ROI (retorno de inversión):
    20 cristales de inversión → +40 XP/h ganados → Se recupera en 30 min de trabajo

3. Decidir prioridad:
    ¿Vale la pena? ¿Tenemos 20 crystals disponibles?
    ¿O esperamos y seguimos farmeando?

4. Automatizar en autopilot:
    Si crystals >= 20 AND efficiency < 80% → Auto-comprar herramienta

⚙️ Arquitectura del Sistema

Documentación técnica completa del autopilot para desarrollo e iteración futura.

🔄 FLUJO DE EJECUCIÓN

1. GitHub Actions Cron dispara
*/10 * * * * (cada 10 min) → autopilot
0 12/4 * * * → reporte (9am, 1pm, 6pm, 9pm ARG)
2. Vercel endpoint recibe request
/api/r2-autopilot o /api/r2-report
3. Conecta a Midnight City API
https://midnight.city/observer con MCITY_API_TOKEN
4. Lee estado actual de agentes
Llama a /api/skill/agents/{id}/context/needs/inventory/progression
5. Ejecuta lógica de mantenimiento
Una acción por ciclo: runConnectedMaintenance() en lib/mcity-maintenance.js
6. Envía resultado a Telegram
Solo si es reporte (4x/día) con timestamp y estado de flota

📝 CÓDIGO DE DECISIÓN (Lógica)

PRIORIDAD 0 (EMERGENCIA):
if (hunger > HUNGER_EAT_THRESHOLD)
→ Comprar comida o ir a dormir
PRIORIDAD 1 (SOBRECARGA):
if (overloaded || workSpeedPercent < 80)
→ Vender inventario inmediatamente
PRIORIDAD 2 (PRODUCCIÓN):
if (in_correct_location)
→ Ejecutar skill (hacking, mining, woodcutting)
PRIORIDAD 3 (COMERCIO):
if (inventory_good && ready_to_sell)
→ Vender a merchant y reiniciar ciclo
⚡ ESPECIAL BB-8:
Usa workSpeedPercent < 80 en lugar de excessWeight
(cambio v2.3 del 2026-09-23)

🚨 TROUBLESHOOTING

❌ Cron no disparó
→ Ver GitHub Actions → workflow → Ver último run
→ Si falta, es porque GitHub Actions tuvo delay (puede pasar)
❌ API devuelve 404
→ Midnight City API puede estar down
→ Vercel env vars pueden estar incorrectas
→ Agent IDs pueden haber cambiado
❌ Telegram no recibe mensaje
→ TELEGRAM_BOT_TOKEN o TELEGRAM_CHAT_ID incorrectos
→ Bot fue removido del chat
→ Vercel env vars no se actualizaron
❌ Agent se queda atrapado
→ Revisar protocolo en mcity-maintenance.js
→ Aumentar umbral de hambre o sobrecarga
→ Cambiar trigger de venta (ver BB-8 como ejemplo)
